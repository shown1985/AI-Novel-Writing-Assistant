## 3. 问题成因分析

### 成因 1：“完成”的定义依赖用户，你永远无法自己达成

几乎每个条目的终点都是“待用户验收”。但用户从没收到过一份可以直接执行的验收包：要打开哪个页面、点什么、看到什么算通过。
结果是条目停在“待验收”，你无事可做，只能去找下一个能写代码的问题。**Agent 会自然地往自己能推进的方向走，而写新代码永远比收尾容易推进。**

### 成因 2：没有唯一事实源，也没有范围闸门

`TASK.md` 是主线清单，`github-issue-expectations.md` 又自成一套 WGR 台账，两者互不引用。`TASK.md` 从 09-01 起没有更新，台账却越写越长。
每次新会话看到的“当前任务”取决于先读了哪份文件。真实模型回放发现问题时，没有“这是否属于当前阶段”的判断步骤，直接开新条目。

### 成因 3：流程规则被机械执行到微小条目上

`AGENTS.md` 要求每个阶段提交、更新文档、走分支流程。你把它套在每个 WGR 小条目上：一条一个分支、一个叠加 PR，外加若干 `docs(plan): link PR` 提交。
流程成本超过了产出本身，而且叠加 PR 的结构决定了：只要底层 PR 没合，上面所有 PR 都显示“未合并”。**看起来什么都没完成，实际上代码早已全部进入 `main`。**

### 成因 4：“本机禁止推送”与“推送到个人仓库”之间的事实源混乱

`TASK.md` 说后续提交只保留在本地，但 WGR 工作又推送到了个人仓库并开了 PR，最终由用户直接合并到 `beta` 和 `main`。
本地、个人仓库分支、PR、`beta`、`main` 五处状态各不相同，你没有做过一次对账，所以无法判断什么已经完成。

### 成因 5：外部接入问题（新模型供应商）把主线拖进了无底洞

OpenCode Go、GLM-5.3-Flash、DeepSeek V4 的参数差异带来一连串问题：推理额度耗尽、`thinking` 参数被拒、请求过大、会话头等。这些问题确实需要修，但它们属于“模型接入层稳定性”，不是“完成一本小说”的主线。
没有给它设上限（比如“只支持一个默认供应商跑通即可”），就会一直修下去。

## 4. 工作纪律（从现在起必须遵守）

1. **唯一事实源**：`TASK.md` 是唯一的当前任务清单。WGR 台账只记录条目细节，每个进行中的条目都必须在 `TASK.md` 里有对应行。`TASK.md` 里没有的事情，不做。
2. **同一时间只有一个进行中条目**：一个条目完成（合入并验证），或者明确搁置并写明原因，才能开始下一个。
3. **“待用户验收”必须附验收包**：每个进入“待用户验收”的条目，必须在 `docs/checkpoints/user-acceptance-checklist.md` 里有对应的操作步骤，写清入口页面、操作、预期结果和失败时看哪里。没有验收包就不能标“待用户验收”。
4. **“待用户验收”最多 3 条**：超过 3 条时停止开发新代码，转去整理验收包、协助用户验收，或者把能自动验证的部分自动化。
5. **范围闸门**：真实运行中发现的新问题，先判断它是否阻塞当前主线（`TASK.md` 当前阶段）。
   - 阻塞：在 `TASK.md` 当前阶段下加一行，在当前分支修复。
   - 不阻塞：写进 `TASK.md` 的“待排期”区，不开分支、不开 PR、不写代码。
6. **不再使用叠加 PR**：每个功能分支都从最新的 `main`（或 `beta`）切出，PR 的 base 只能是 `beta`（或 `main`）。
7. **不写只为挂链接的文档提交**：PR 链接、验证证据随代码提交一起更新，或者在阶段收尾时一次性更新。
8. **状态必须对账**：每个阶段结束时，核对“本地 / 远程分支 / PR / `beta` / `main`”五处状态，把台账状态改成真实情况。
9. **诚实汇报**：没有真实运行过的验证，写“未验证”；用户没有验收的，写“未验收”。不得用“待验收”代替“未完成”。

## 6. 系统功能如何归一完成

### 6.1 产品只有一条主线

本产品的目标只有一个：**让完全不懂写作的新手，从一句灵感走到一本完整的小说**（见 `AGENTS.md` 的 Product Context）。所有功能都必须挂在这条主线上：

```
一句灵感
  → 书级设定（题材、推进模式、写法、世界观、角色）      setup
  → 分卷与章节规划                                        planning
  → 自动导演驱动章节生产（生成 → 审核 → 修复 → 保存）    director + production
  → 质量债记录与恢复                                      state
  → 导出成书                                              export
```

- **世界观生成**不是独立产品，它是书级设定里的一个步骤（`world_setup` 已作为导演运行时的工作流步骤接入）。它的完成标准是：主线跑到这一步时能稳定产出可用的世界观，失败时能从源页面继续。**不追求**覆盖所有模型、所有规模的最优效果。
- **模型接入**是基础设施。它的完成标准是：一个默认推荐的供应商组合，能在 Windows 和 Mac 上稳定跑完整条主线。其他供应商只保证“能配置、出错时有清晰提示”，不为每个模型单独开条目。
- **桌面打包**是分发渠道。它的完成标准是：安装、首次配置、重启后数据保留都能通过，不在打包问题上扩展新功能。

### 6.2 “系统完成”的判定标准

满足以下全部条件，才能称当前版本“主线完成”：

1. 在 Windows 和 Mac 桌面版上，新用户只做一次模型配置，就能从一句灵感启动自动导演。
2. 自动导演连续生成至少一整卷（先以 10 章为第一道门槛，再以完整一卷为最终门槛）；过程中局部质量问题只记录为质量债，不中断整本生产。
3. 中途关闭应用或模型暂时不可用后，能从源页面恢复，且不重复生成已完成的章节。
4. 运行记录（任务中心）、AI 驾驶舱、简易模式和专业模式显示同一个状态和同一个恢复入口。
5. 最终能导出为 TXT。
6. `main` 上构建、类型检查和定向测试全部通过，没有超过 1300 行的源文件。

在这 6 条全部满足之前：

- 不开新的创作能力（漫画、短剧、拆书扩展等计划保持搁置）。
- 不为新的模型供应商开专门条目。
- 所有新发现的问题，按第 4 节第 5 条的范围闸门处理。

### 6.3 分支模型（归一后）

```
main   ← 只接收经过 beta 验证的合并
  ↑
beta   ← 当前候选版本，组合回归与真实链路验收在这里完成
  ↑
feature/<一个主题>   ← 同一时间只有一个，从 beta 切出，合入 beta 后立即删除
```

- 不再使用 `fix/*` 与 `codex/*` 两套前缀并存的方式，统一为一个主题一个分支。
- 功能分支合入 `beta` 后当天删除；PR 合并或关闭后，分支同步删除。
