## 全范围分解约定

- “全部”指本路线图的PREP-01～04、S1～4各原Story、B-01～12及新增模型能力评测项；不是把仓库所有历史计划或未提出的新功能纳入本期。
- Spike 与其后的生产建设卡都列出；前置能力缺失不能只写“以后补”而省掉任务。
- 一张实施卡围绕一个可验收结果，估点不超过5；父ID只汇总，不是重复交付。细分增加显式接线/迁移/兼容成本时，重新估算而不固守原概要数字。
- Story分解完成、合同已冻结、业务已完成、UI验收、beta集成分别记录。待解锁卡可准备测试和mock，但不能执行未受保护的写入或对外发布入口。
- 新风险若在实施中发现，新增明确ID并更新映射和容量；不在旧卡里悄悄扩大范围。并发Agent每次只领取已解锁的一张或一个同owner串行阶段。

## 已确定的产品规则

1. 作品以已保存成果为中心；正文默认可读，资料和协作区域按需展开。
2. 每个现场只有一个推荐主动作，允许作者自由表达；普通内部调用不逐项审批。
3. 不新增首章前的专业审批。世界准备标准由 AI 根据题材、篇幅和作品承诺解释，不能统一要求能力体系或势力数量。
4. 本次委托明确对象、范围、允许改变与必须保留的内容。重要方向变化和保护冲突回到来源现场处理。
5. 区分事实、人物认知、计划、AI 推断、试演；允许刻意留白和暂不决定。
6. completion-first 的局部质量债可继续；quality-first 明确的人工暂停仍须显式恢复。
7. 全局 Creative Hub 只读查询导航，运行记录只读；执行协作属于作品、章节或资产来源工作台。
8. 世界样本与本书实例隔离，生成链通过 WorldContextGateway 读取本书世界。后续同步必须明确选择方向与范围。
9. 设置读取不调用付费模型，不自动应用检测建议。模型来源和有效参数可追溯。
10. 已发布稿和作者保护内容不得被自动覆盖；撤回范围必须由真实版本和依赖能力支持。

### PREP-01：产品共识留档（规划已完成）

- Owner：PO/根集成人；价值：避免各 Agent 为不同作者假设设计不同产品。
- 子任务：记录三作者代理多数意见；分清设计同意和实际验收；落实正文优先、委托范围、留白与质量策略。
- 验收：代理评审明确标为模拟视角；任何新入口不新增首章专业审批；来源现场执行与全局只读边界写入稳定Wiki；三种作者需求均能映射到验收场景。
- 检查/证据：产品Wiki与任务卡交叉复核，无真实用户调研结论或业务已实现声明。
- 非范围：真实作者访谈、真实模型效果和首章速度测评。

### PREP-02：现有代码与风险审计（规划已完成）

- Owner：交互/AI/Runtime三个审计Agent，根集成人集成。
- 子任务：核对实际入口与权限、配置和模型选择、版本/历史/恢复；关联真实路径与待验证风险。
- 验收：每项风险有源码而非设计猜测；归属安全缺陷单独P0；超长文件在扩展前拆分；旧快照与手动状态不得冒充全局撤回或验证完成。
- 检查/证据：只读审计结果与本文前置问题表；开工基线变化时重核受影响证据。
- 非范围：模型探测、用户库写入与修复实施。

### PREP-03：任务分解与并发所有权（文档已完成，生产接线待 S1-00）

- Owner：根集成人；价值：任务可以派发且不会多人同改共享契约。
- 子任务：为所有原始ID建立详细卡；超过5点或多责任卡拆分；标出依赖与前置Spike；共享文件集中接线。
- 验收：S1～4与B-01～12均有详细卡且不重复计点；卡有用户价值/实施任务/AC/检查/非范围/证据；拟建模块与现有路径明确区分；未决合同标待解锁；并发波次不同时写相同文件。
- 检查/证据：文档链接与来源ID覆盖检查、三路审阅；类型和迁移尚未接线时不宣称Ready。
- 非范围：业务实现、所有后续API/schema一次冻结。

### PREP-04：验证与交付门（规划已完成，功能验收待各 Story）

- Owner：根集成人/验收Owner；价值：完成标记来自真实证据而非仅编译成功。
- 子任务：建立mock与隔离库方案、失败与并发行为回归、用户UI清单、beta组合门及阶段提交范围。
- 验收：测试禁止用户库和默认付费调用；UI不默认跑浏览器；命令对应真实包与测试而非占位原样执行；feature验证不等于beta集成；真实模型抽样与确定性回归分开。
- 检查/证据：各实施卡验证段与本文Ready/Done合同；本阶段仅文档检查，不伪报build通过。
- 非范围：自动晋级beta/main、包装上传或公开发布。

S1-06 的世界维护运行承接与新增数据模型仍需 Spike 决策，后续 Story 未冻结前不能开始相应生产代码。

## 多 Agent 执行与集成

首轮固定三条可并行工作流：

- Agent A：S1-01 数值配置与对应行为测试。
- Agent B：S1-02a、02b、03 诊断后端/设置页面；这些卡存在相同文件，不拆给两人同时写。
- Agent C：S1-04 阅读恢复；完成后才考虑 S1-X。
- 根集成人：S1-00共享类型、API/queryKeys、迁移审查、S1-05、S1-06、集成验证、Wiki、发布记录、阶段提交。

共享文件采用单一 owner。Agent 需要改 shared/types、registry、Prisma schema、API facade、路由挂载、README 或发布记录时，先提交结构化修改请求，由根集成人依赖顺序接线。不能互相覆写或回退。

后续世界 Sprint 在冻结合同后切换为 Runtime、Prompt、UI 三 Agent；Runtime 独占事务和恢复，Prompt 独占资产与输出 schema，UI 消费接口。主集成人审阅跨模块影响。

分支策略：

1. 规划分支保存文档；实施使用短期 codex/ 功能分支，记录准确基线。
2. 当前基线含未晋级的既有工作。进入 beta 前审查完整差异与来源，不把规划或功能分支的继承提交自动当作已验证。
3. 单一 checkout 并发时子 Agent 不 switch/merge/commit；根集成人审阅后按完成阶段提交。需要独立分支时由根集成人创建隔离 worktree 并指定路径。
4. 验证后 feature → beta，组合验收后再到 main。分支晋级、发布、破坏性迁移不委托给子 Agent。

## Ready 与 Done

Ready：用户价值、范围、接口/数据来源、依赖、ownership、验收、最窄检查已明确；依赖未冻结则只能做 Spike 或 mock 联调。

Done：真实写入/读取/投影/恢复符合 Story；定向行为检查通过；用户 UI 验收或未验收缺口明确记录；Wiki/发布记录按影响维护；只提交本阶段范围。功能未联通、付费模型未实测、beta未组合测试必须明确，不能用 typecheck 替代。

模型与数据库测试使用 mock transport、mock persistence 或隔离临时 SQLite；不使用用户桌面库运行写入测试，不 reset、不覆写已保存正文。任何破坏性步骤遵守备份与授权规则。

前端不默认跑浏览器/截图；用户执行 UI 验收。共享/server/dist 变更后由集成人统一构建一次，再运行对应测试，避免各 Agent 重复昂贵检查。
