# Agent 分级交付流程

## 背景

Release 1 的 R1-S0～R1-S3L 对所有工作都执行完整敏捷流程：Story 合同、独立 DoR、独立 QA/QC、Sprint 承诺与 Review/Retrospective。22 个 Sprint 共 153 点全部按承诺完成，但暴露出两个问题：

- 对普通修复来说，仪式成本高于它提供的保护。S3J～S3L 的返工多为 DoR 轮次和合同边界修订，而不是用户可感知的缺陷；一个已经能用的功能（AI 结构补全）被拆成约十张内部底座卡，生产入口仍未受保护。
- 优先级来自预先写好的 Story 列车，而不是真实使用。完整链路（想法 → 自动导演 → 连续写章 → 暂停/恢复 → 导出）从未用真实模型端到端跑通，底座投入无法证明解决了用户实际会碰到的问题。

## 决策

流程按改动风险分级，优先级由真实端到端试跑决定。

| 级别 | 适用范围 | 流程 |
| --- | --- | --- |
| 完整流程 | 数据/迁移、发布/打包、运行时或 Prompt 合同（运行时状态、任务恢复、结构化输出 schema、Prompt Registry、共享类型） | DoR → 实现 → 独立 QA → 合并 → 简短 Review |
| 普通流程 | 普通缺陷、体验问题、试跑中发现的问题、文案与局部 UI | 实现 → 一次评审 → 合并，不写 Sprint 或 Story 合同 |

完整流程只保留仍有保护价值的部分：

- DoR 写清用户价值、范围与非范围、依赖、验收条件、文件边界和最窄验证。
- 单张实现卡不超过 5 点，大工作拆成可独立验收的纵向切片。
- 共享 schema、迁移、Registry、共享类型和路由挂载只有一个集成 owner。
- 独立 QA 核对成功、失败、重试、并发与恢复路径；typecheck 或 build 不能代替行为证据。

两级共同要求：每个改动一个范围明确的阶段提交；用户可见 UI 标明验收状态；发现的相邻问题进入 backlog，不顺手扩大范围；数据保护规则不因分级放宽。

## 为什么这样分

- 数据迁移、发布和运行时/Prompt 合同出错的代价是用户数据损坏、错误安装包或整条生产链中断，且难以回滚，所以值得前置合同与独立验收。
- 普通缺陷修复影响范围小、容易回滚；一次评审就能拦住大多数问题。完整仪式只会拖慢反馈。
- 真实试跑暴露的问题才是新手用户会碰到的问题。先跑通链路，再按严重度排队，比按计划顺序建设底座更贴近“帮新手写完一本书”的目标。

## 失败模式

- **把合同变更当普通修复**：改动触及迁移、恢复状态或结构化 schema 却走普通流程。评审时发现应立即升级到完整流程。
- **用计划代替试跑**：在没有真实使用证据时继续扩写 Story 列车。候选 Story 只作为参考，试跑结果决定先做什么。
- **分级后跳过证据**：普通流程也要有能复现问题和验证修复的最小检查，不能只凭“看起来改好了”。
- **在 Story 中顺手扩大范围**：发现的问题记入 backlog，另行处理。
